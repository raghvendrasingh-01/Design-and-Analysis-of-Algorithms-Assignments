## Introduction

This repository is my running record of the Design and Analysis of Algorithms
Laboratory at IIIT Bhubaneswar. Every lab session gets its own folder, and each
folder holds the source files written for that session's problem set.

DAA is less about getting a program to run and more about showing how it behaves
as the input grows. So most programs here do two jobs at once: they solve the
problem, and then they instrument themselves — counting comparisons, counting
moves, tabulating values across decades of `n` — and export that data as CSV so
the growth can be plotted rather than asserted.

## About the Repository

- Written entirely in **C**, compiled with **GCC**.
- One directory per lab session (`WEEK 1`, `WEEK 2`, …), each containing the
  question paper alongside the solutions.
- File names describe the problem, not just the question number — e.g.
  `q4_towers_of_hanoi.c` rather than `q4.c`.
- Programs that study growth write their measurements to a **CSV** file, which is
  then plotted and committed as an **SVG** next to it.
- Every program closes by printing its own time and space complexity, so the
  analysis travels with the code rather than living in a separate note.
- No external libraries — only the C standard library.

## Highlight — Q1 does the ordering twice

`q1_growth_order.c` is the longest program in the repository, and deliberately so:
instead of hardcoding the expected answer, it **derives the ordering twice by two
independent routes and then confronts the two results.**

- **Pass 1 — numerically.** Each of the 12 functions is evaluated at
  `n = 10²` through `10⁸` and sorted at every decade. Because `3ⁿ` and
  `n^(log₂ n)` overflow a `double` almost immediately, ranking is done on a
  closed-form `log₁₀(f(n))` *magnitude* instead of the value itself, so every
  function stays comparable at every scale.
- **Pass 2 — asymptotically.** The same array is sorted again using only each
  function's declared growth class and exponent, ignoring numeric values
  entirely. Genuine ties are reported as ties rather than broken arbitrarily.
- **Sorting.** Both passes share one hand-written **stable merge sort** that is
  generic over a function-pointer comparator — `qsort` is never used, so the
  sort itself is part of the answer.

The interesting result is that the two passes **agree on only 5 of 12 positions**
at `n = 10⁸`:

```text
Asymptotic order (Pass 2):
1/n < log2(n) < 12*sqrt(n) = 50*n^0.5 < n^0.51 < (2^32)*n
    < n*log2(n) < 100*n^2+6*n = n^2-324 < 2*n^3 < n^(log2 n) < 3^n

Numerical order at n = 10^8 (Pass 1):
1/n < log2(n) < n^0.51 < 12*sqrt(n) < 50*n^0.5 < n*log2(n)
    < n^2-324 < (2^32)*n < 100*n^2+6*n < 2*n^3 < n^(log2 n) < 3^n
```

That gap is the whole point of the exercise. `n^0.51` must eventually overtake
`12√n`, and `n²−324` must eventually overtake `2³²·n` — but at `n = 10⁸` neither
crossover has happened yet, because the constants still dominate. The program
reports the disagreement instead of hiding it, along with a rank-movement table
showing which functions were still changing position at the largest `n` tested.

Output also includes an ASCII bar graph on a log-of-log scale, so the six growth
classes separate visually in the terminal.

## Results and Artifacts

The three simulation programs export their measurements; the plots are committed
next to them.

| Data | Plot | Produced by | What it shows |
|------|------|-------------|---------------|
| [coin_toss_analysis.csv](WEEK%201/coin_toss_analysis.csv) | [coin_toss_analysis.svg](WEEK%201/coin_toss_analysis.svg) | Q2 | Observed vs expected head-frequency for five biases (50, 60, 70, 90, 30 %), as a grouped bar chart. |
| [bubble_sort_analysis.csv](WEEK%201/bubble_sort_analysis.csv) | [bubble_sort_analysis.svg](WEEK%201/bubble_sort_analysis.svg) | Q3 | Share of total comparisons spent by the early-terminating sort vs the full-pass sort. |
| [toh.csv](WEEK%201/toh.csv) | [toh.svg](WEEK%201/toh.svg) | Q4 | Moves against number of discs, 1 → 25, as a line plot. |

A few conclusions that fall out of the data:

- **Law of large numbers (Q2).** Over 100,000 tosses per coin, the observed head
  frequency never drifts from its programmed bias by more than **0.00079** — the
  fair coin lands at 0.50045 against an expected 0.50.
- **Early termination is a constant-factor win, not a complexity win (Q3).** On
  the recorded run the early-stopping sort used **63** comparisons against **66**
  for the unconditional version. Both remain Θ(n²) in the worst case; skipping
  trailing passes only helps once the array is already sorted.
- **The recurrence is exact (Q4).** `T(n) = 2·T(n−1) + 1` solves to `2ⁿ − 1`, and
  the simulated move count matches the closed form for **all 25 rows** — 25 discs
  take 33,554,431 moves. Plotted linearly the curve is visibly exponential.

## Complexity Summary

| # | Program | Time | Space |
|---|---------|------|-------|
| 1 | Growth ordering (merge sort over 12 functions, 7 scales) | Θ(T · F log F) sorting, plus Θ(T · F²) for the rank-movement pass | Θ(F · T) for the cached value and rank matrices, plus an Θ(F) merge buffer |
| 2 | Coin toss simulation | Θ(n) in the number of tosses | Θ(1) |
| 3 | Bubble sort — early termination | Ω(n) best, O(n²) worst | Θ(1) auxiliary |
| 3 | Bubble sort — full passes | Θ(n²) always | Θ(1) auxiliary |
| 4 | Towers of Hanoi | Θ(2ⁿ) moves | Θ(n) recursion depth |
| 5 | Partition point (binary search) | Θ(log n) | Θ(1) |
| 6 | Element uniqueness (brute force) | O(n²), exactly n(n−1)/2 comparisons in the worst case | Θ(1) auxiliary |

## Compilation and Execution

```bash
cd "WEEK 1"

# Q1 uses log/pow/sqrt, so it needs the math library
gcc -Wall -Wextra q1_growth_order.c -o q1 -lm
./q1

# Q2 to Q6 need no extra linkage on GCC
# (Q2 calls fabs(), which GCC inlines; add -lm if your toolchain does not)
gcc -Wall -Wextra q4_towers_of_hanoi.c -o q4
./q4
```

Recommended flags while working:

```bash
gcc -std=c11 -Wall -Wextra -O2 file.c -o out -lm
```

**On Windows** (MinGW-w64), replace `-o q1` with `-o q1.exe` and run `q1.exe`.

**Note on generated files.** Q2, Q3 and Q4 write their CSV into the *current
working directory* under a fixed name (`coin_toss_analysis.csv`,
`bubble_sort_analysis.csv`, `toh.csv`). Running them from inside `WEEK 1` will
overwrite the committed copies. Build and run from a scratch directory if you
want to keep those files untouched:

```bash
mkdir -p /tmp/daa && cd /tmp/daa
gcc -Wall -Wextra "$OLDPWD/WEEK 1/q4_towers_of_hanoi.c" -o q4 && ./q4
```

Q1 prints its full report to standard output and writes nothing.
